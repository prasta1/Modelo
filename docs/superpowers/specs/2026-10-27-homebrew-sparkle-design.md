# Homebrew install + Sparkle in-app updates — design

Date: 2026-10-27 · Status: approved in chat, awaiting plan

## Intent

Modelo shipped its first Developer ID-signed, notarized build (v0.3.1) on
2026-10-27. `.github/workflows/release.yml` builds it and attaches
`Modelo-vX.Y.Z.zip` to a GitHub release whenever a `v*` tag is pushed. Two gaps
remain:

1. **No way to hear about new versions.** Someone who downloaded v0.3.1 stays on
   it until they happen to check GitHub.
2. **One install route.** Developers expect `brew install --cask`.

Most people will still download the zip from GitHub. Homebrew is an extra route,
not a replacement. Both are listed under "Coming soon" in the v0.3.1 release notes.

## Goals

- **Sparkle in-app updates.** Modelo notices a new release, shows its notes,
  and on **Install Update** downloads it, replaces itself and relaunches. (User's
  call: Sparkle installs the update; just linking to GitHub is not enough.)
- **Homebrew cask** in the user's own tap: `brew install --cask prasta1/modelo/modelo`.
- **Zero manual release steps.** Pushing a tag still does everything: build,
  notarize, publish, appcast, and the cask bump.

## Non-goals

- Official `homebrew/cask` submission. Homebrew wants roughly 75 stars or
  30 forks; Modelo has 6 and 2. Revisit later.
- Beta / pre-release update channel, delta updates, DMG packaging.
- Mac App Store.

## Anti-goals (failure even if it "works")

- **Installing without consent.** No update ever installs without a click, and
  nobody is opted into background checks silently.
- **Updates that break secrets.** An update must not drop the
  `keychain-access-groups` / `com.apple.application-identifier` entitlements.
  If they go, API keys fall back to the legacy keychain and macOS prompts for a
  password (see `Modelo/Modelo.entitlements`, AGENTS.md).
- **Homebrew and Sparkle fighting.** A brew-installed copy that Sparkle updates
  must not leave `brew` confused or downgrade it on the next `brew upgrade`.
- **An update path an attacker can use.** Every update must be verified by
  Sparkle's EdDSA signature, in addition to Developer ID.
- **Manual steps creeping back** into releasing.

## Constraints (current state)

- Native macOS SwiftUI app, macOS 14+, universal (arm64 + x86_64). The Xcode
  project is generated by XcodeGen from `project.yml` and is not committed.
- **Not sandboxed** (no `com.apple.security.app-sandbox`). Hardened Runtime is on.
- Release signing: automatic signing for the archive, then **manual** Developer
  ID export via `scripts/ExportOptions.plist` with the `Modelo Developer ID`
  profile. Automatic export fails in CI with "Cloud signing permission error".
  Don't regress this.
- `Info.plist` is explicit (`Modelo/Info.plist` + `info.properties` in
  `project.yml`), so Sparkle keys go in `project.yml`.
- **Dependencies are a deliberate exception**: only MarkdownUI and Highlightr
  today (comment in `project.yml`). Sparkle becomes the third. The user chose
  Sparkle explicitly; record why in the `project.yml` comment.
- Release notes are generated, reversed newest-first, and end with a SHA-256
  line (publish step in `release.yml`).
- The menu bar is built in `Modelo/ModeloApp.swift` `.commands { … }`.
- User data: SwiftData store in `~/Library/Application Support/Modelo/`
  (legacy `ModeloDos/`), bundle ID `com.peregrine.modelo`, secrets in the
  data-protection keychain.

## Order

Two independent pieces. **Homebrew first** because it's smaller and needs no app
code. Then Sparkle. Each ships on its own branch/PR.

## Part 1 — Homebrew tap

**Decided:**
- New **public** repo `prasta1/homebrew-modelo` holding `Casks/modelo.rb`.
  Homebrew maps `prasta1/modelo` to that repo name.
- The cask downloads the existing release zip:
  `https://github.com/prasta1/Modelo/releases/download/v#{version}/Modelo-v#{version}.zip`,
  with `sha256`, `depends_on macos: ">= :sonoma"`, `app "Modelo.app"`, and a `zap`
  stanza for the paths above plus the `com.peregrine.modelo` preferences.
- First cask is written by hand for **v0.3.1**, so brew works immediately.
- `release.yml` gains a final step that rewrites `version` and `sha256` in the
  cask and pushes to the tap. `GITHUB_TOKEN` can't push to another repo, so
  this needs a new secret **`TAP_TOKEN`**: a fine-grained PAT with Contents:
  write on `prasta1/homebrew-modelo` only. The user creates it; give them
  click-by-click steps, as was done for the other secrets.
- README **Install** gets the brew command beside the download link.
- Until Sparkle ships, `auto_updates` is absent and `brew upgrade` is the update
  path for brew users.

**Done when:** on a clean Mac, `brew install --cask prasta1/modelo/modelo` installs
a Gatekeeper-accepted v0.3.1, and the next tag push bumps the cask with no hand edits.

## Part 2 — Sparkle

**Decided:**
- **Sparkle 2.x via SPM**, added in `project.yml`.
- **UI:** Sparkle's standard update window (release notes, Install Update /
  Remind Me Later / Skip This Version) and a **Check for Updates…** item in the
  app menu under "About Modelo".
- **Consent:** leave `SUEnableAutomaticChecks` unset, so Sparkle asks once (on
  the second launch) whether to check automatically. Default interval: daily.
- **Feed:** `SUFeedURL` =
  `https://github.com/prasta1/Modelo/releases/latest/download/appcast.xml`.
  Each release attaches its own `appcast.xml` with just that version. GitHub's
  `latest` redirect means nothing else needs hosting.
- **EdDSA signing:**
  - The user generates the key pair once with Sparkle's `generate_keys`.
  - The public key goes in `SUPublicEDKey`.
  - The private key becomes a new secret **`SPARKLE_ED_PRIVATE_KEY`** and is
    backed up in the user's password manager.
- **Workflow:** after notarize + staple, `release.yml` signs the final zip
  (Sparkle `sign_update`), writes `appcast.xml`, and attaches both to the release.
  - `sparkle:version` = `CFBundleVersion` (`CURRENT_PROJECT_VERSION`).
  - `sparkle:shortVersionString` = `MARKETING_VERSION`.
  - `sparkle:minimumSystemVersion` = `14.0`.
- **Build number must increase every release.** Sparkle compares
  `CFBundleVersion`, not the marketing version. Document this in AGENTS.md →
  Releasing, next to the existing MARKETING_VERSION ↔ tag rule.
- **Homebrew:** once the first Sparkle release ships, the cask gets
  `auto_updates true` (via the workflow step from Part 1). `brew upgrade` then
  leaves Sparkle-updated copies alone.
- **Bootstrap:** v0.3.1 has no Sparkle. The first Sparkle release's notes tell
  users to download it once by hand; after that, updates arrive in-app.

**Done when:**
- An installed build N, pointed at a feed for build N+1, shows the update
  window, installs and relaunches into N+1.
- After the update, secrets still load from the keychain with no password prompt.
- A tampered zip, or one with a bad EdDSA signature, is rejected.
- The real tag-push release produces a valid `appcast.xml` asset.

## Left to the builder

- Where `sign_update` / `generate_appcast` come from in CI: the SPM artifact
  under DerivedData, or a pinned Sparkle release download. Pin the version either way.
- Hand-templating `appcast.xml` vs. running `generate_appcast`.
- What the appcast shows as release notes: `sparkle:releaseNotesLink` to the
  GitHub release page, or the notes embedded as HTML.
- How to test Sparkle end-to-end without publishing a real release. `/releases/latest`
  ignores pre-releases, so use a local feed (a feed-URL override or the updater
  delegate's feed URL, in Debug only).
- Whether the workflow should fail if `CURRENT_PROJECT_VERSION` didn't increase
  over the previous release's appcast.
- Exact Swift placement of the updater controller (an `SPUStandardUpdaterController`
  owned by the app, exposed to the command).
- Confirming that Developer ID export + notarization sign Sparkle's embedded
  helpers (Autoupdate, Updater.app) correctly. Notarization will flag them if not.
